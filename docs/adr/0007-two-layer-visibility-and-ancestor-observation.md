# 可见性分两层：呈现挂起与祖先观察

与同页组件 bangumi-user-topics 的冲突暴露了 ADR 0002 的盲区：topics 接管时在 `#wrapperNeue` 上翻转 `data-user-topics-active`，由样式表把 `.mainWrapper` 中 footer 之前的宿主节点（含好友列表与排序栏）整体隐藏，`#memberUserList` 子树内没有任何属性变化，子树观察必然漏掉，排序栏会对不可见的列表继续重排与改写名次。现在把可见性拆成两层：整个好友视图是否可呈现（呈现挂起，见 GLOSSARY.md）与单个好友是否可见（ADR 0002 的可见好友）；两层最终是否可见统一由 `checkVisibility()` 判定，条目不可用时回退到内联 display 检查（回退下祖先驱动的显隐不可感知，属可接受降级）。渲染入口先做列表层检查：不可呈现即进入呈现挂起，只保留最新可呈现状态、把排序与可见性呈现缓存标记为未知（`null`；`[]` 继续专指活动状态下确实没有可见好友），跳过列表 DOM 重排与名次更新，排序栏自身呈现（选中态、方向文案、状态提示）照常更新；恢复可呈现后重放最近一次渲染，凭 `null` 缓存语义从真实 DOM 开始 reconciliation，一次补齐错过的重排与名次。观察分两路：原有子树观察继续处理 friend-tag 一类列表内局部筛选；另增一个观察器覆盖列表之上的每个祖先直到文档根，不过滤属性名（style/class 过滤会漏掉 `data-*` 标记），回调先做廉价的列表级表现状态门控，状态未变即早退，变化才重放——真值唯一归 `checkVisibility()`，观察器只负责触发。

被拒的备选：祖先观察止于 `#wrapperNeue`——省两个 observe 目标，代价是赌「文档根与 `#wrapperNeue` 之间永远不会有显隐驱动属性」，topics 本身就是这类意外，门控已把每次回调压到一次单元素检查，覆盖面应当拉满；attributeFilter 限定 style/class——与本次改动的起因直接矛盾，且与 ADR 0002「不与任何组件建立属性名契约」的姿态不一致；由会话层感知挂起并暂停任务——把 DOM 可见性泄漏进领域层，数据获取与数据呈现本就是两层；恢复时清空再重写状态提示以避免屏幕阅读器播报挂起期间的提示——恢复后该提示仍是会话当前真实状态，为它加特殊路径不值得。

后果：排序栏对外的「名次始终匹配可见顺序」承诺（ADR 0002）扩展为「可呈现时始终匹配」；挂起期间到达的排序命令与刷新结果只更新状态与缓存，呈现延迟到恢复后一次性补齐；任何以无属性变化的方式切换显隐（`:has()` 跨兄弟选择、样式表热替换）仍不可感知，与 ADR 0002 的残余风险相同。
